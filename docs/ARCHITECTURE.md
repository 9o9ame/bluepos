## 2. Architecture decisions

### 2.1 Style

**Modular monolith.** One Laravel 13 API, one PostgreSQL database, one React PWA. Domain folders inside the monolith. **No microservices** at this stage.

Two operator surfaces, one API:

1. **Tenant application** — mart staff. Ribbon + tab workspace. Offline-capable POS terminals.
2. **Platform / Super Admin application** — tenants, plans, modules, licenses, health. Online only. No casual access to mart financial documents.

### 2.2 Target stack

**Frontend**

- React, TypeScript, Vite, Tailwind CSS
- React Router, TanStack Query
- React Hook Form, Zod
- Dexie.js / IndexedDB
- PWA service worker

**Backend**

- Laravel 13, PHP 8.3+
- REST API
- Laravel Sanctum **session authentication** for the browser SPA
- Registered POS device tokens (Sanctum personal access tokens) bound to `devices`
- PostgreSQL (system of record)
- Redis for cache and queues where available; `database` queue driver is an allowed local fallback

**Money**

- Canonical persist type: PostgreSQL `NUMERIC(20,4)`. **Never** `FLOAT` / `DOUBLE` / `REAL` / `NUMERIC(19,4)`.
- Working calculation: BCMath scale 8; round half-up to 4 only at line/invoice/payment steps in `docs/DATABASE.md` §14.4.
- Display: tenant `currency_display_decimals` (default 2 for PKR). Display ≠ storage.
- React previews totals. Laravel recomputes price, qty, discount, tax, lines, invoice, payments, COGS, profit.

**Quantity**

- Canonical: `NUMERIC(20,6)`. **Never** `NUMERIC(18,4)`.
- `allows_decimal=false` is validation only; column type unchanged.

**Percent / conversion**

- Canonical: `NUMERIC(12,8)` (tax %, discount %, margin %, conversion_factor).

**Public identifiers**

```text
id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
ulid  CHAR(26) UNIQUE NOT NULL
```

- `id` is internal only. `ulid` is the public resource identifier (Crockford ULID).
- REST APIs never expose BIGINT ids. Route binding uses `ulid`.
- Foreign keys use BIGINT `id`.
- Offline-created resources use ULIDs (`client_ulid`).
- **Do not** name a ULID column `uuid`. Do not introduce RFC UUIDs unless later justified.
- **Do not** use ULID as the primary key.

### 2.3 Explicit non-goals (now)

- Microservices, database-per-tenant, JSON:API as the public contract
- FIFO costing (interface reserved; v1 is moving weighted average)
- Serial-number inventory as a required v1 path
- Stock reservation as a required v1 path (documented for later)
- Copying proprietary POS PLUS assets or source

## 3. Multi-tenancy

### 3.1 Hierarchy

```text
Platform
  Super Admin (platform users)
  Plans / tenant_modules / subscriptions
  Tenant (mart)
    Memberships (user ↔ tenant)
    Roles / permissions (tenant-scoped roles, global permission catalog)
    Branches
      Warehouses
      Devices / POS terminals
      Users assigned via membership_branches
    Catalog, parties, stock, sales, purchases, journals
```

### 3.2 Isolation model

Shared PostgreSQL schema. Every tenant-owned business row has `tenant_id`.

Where the record is operationally local it also has:

- `branch_id`
- `warehouse_id` when stock or a stock-backed document is involved

**Never trust `tenant_id`, `branch_id`, or `warehouse_id` from the request payload as authorization.** They may appear in DTOs for convenience only after the server has already resolved and authorized context. Writes always persist the **session-resolved** tenant and the **authorized** branch/warehouse.

### 3.3 Tenant context resolution

1. User authenticates with Sanctum (SPA cookie session or device token).
2. Session stores `user_id` and selected `membership_id` (user × tenant).
3. Middleware `SetTenantContext` loads the membership: must be `active`, tenant must be `active` (or `trial`).
4. `TenantContext` (request-scoped) exposes `tenantId()`, `membership()`, `user()`, `branchIds()`, default `branchId()`, default `warehouseId()`.
5. Device-bound POS sessions additionally load `devices` row: `status = active`, and **force** branch/warehouse from the device registration (cashier cannot pick another warehouse on that terminal unless permitted and the device is reassigned).
6. Eloquent global scope `BelongsToTenant` applies `where tenant_id = context` on all tenant models.
7. Branch-scoped queries add `whereIn(branch_id, authorized_branch_ids)` unless the role grant is `all_branches`.
8. Route binding looks up by public ULID **inside** the scoped query. Missing row → 404 (not 403 that confirms existence in another tenant).

Platform routes (`/api/platform/*`) do **not** set tenant context from a membership. They use platform policies only.

### 3.4 IDOR controls

| Attack | Defence |
|---|---|
| Guess Tenant B sale ULID | Global scope + ULID lookup → 404 |
| Send `tenant_id` of another mart in JSON | Ignored; context comes from membership |
| Send another `branch_id` | Policy: branch must be in `membership_branches` or `all_branches` |
| Warehouse from another branch | Warehouse.branch_id must match authorized branch |
| Super Admin opens `/api/v1/sales/{ulid}` | Platform users have no tenant membership; 403/404 |
| Change `id` in mass assignment | `tenant_id` / `branch_id` not fillable from request |

Tests in Phase 1+ must include cross-tenant and cross-branch ULID access.

### 3.5 Forbidden vs required lookup pattern

**Forbidden**

```php
$model = Model::findOrFail($request->id); // or findOrFail($request->ulid)
// then only Gate::allows('view') / permission key
```

That ignores tenant, branch, and parent ownership. Sequential or leaked ULIDs become IDOR.

**Required**

```text
authenticated membership
  + tenant scope (global BelongsToTenant / TenantContext)
  + branch scope where the resource is branch-owned
  + parent ownership for nested resources
  + permission key
```

```php
$sale = Sale::query()
    ->where('tenant_id', $tenantId)
    ->where('ulid', $saleUlid)
    ->firstOrFail();
// then policy: branch entitlement + sales.view

$item = $sale->items()
    ->where('ulid', $itemUlid)
    ->where('tenant_id', $tenantId)
    ->firstOrFail();
```

Never load `sale_item` by ULID alone. It must belong to the requested sale, and that sale must belong to the active tenant.

Route binding resolves **by ULID inside the scoped query**. Policies then confirm the resource’s `tenant_id` matches context (defense in depth) and branch/warehouse hierarchy.

### 3.6 Nested ownership (must match)

| Resource | Must belong to |
|---|---|
| `sale` | `tenant` + `branch` (+ warehouse for stocked sales) |
| `sale_item` / `sale_payment` | parent `sale` **and** same `tenant_id` (denormalized, checked) |
| `sale_return` | tenant + branch; if against invoice, `original_sale.tenant_id` and branch rules |
| `sale_return_item` | parent return + original `sale_item` of that sale |
| `warehouse` | `branch` → `tenant` |
| `product_batch` | `product` → `tenant`, and `warehouse` → same tenant |
| `stock_movement` | tenant + branch + warehouse + product + batch (all same tenant) |
| `journal_line` | parent `journal_entry` → tenant |
| `device` | tenant + branch + warehouse |

Never authorize a child by its own ULID alone. Load through the parent or verify `child.sale_id = sale.id` AND `child.tenant_id = sale.tenant_id = context.tenant_id`.

### 3.7 Table scope classification

**GLOBAL (no tenant_id):** `users`, `permissions`, `plans`, Laravel/Sanctum internals.

**PLATFORM-OWNED but tenant-linked:** `tenants` (self), `subscriptions`, `tenant_modules`, `support_impersonations`.

**TENANT SCOPED:** catalog, parties, accounts, roles, settings, sequences, products, barcodes, prices, journals, idempotency, audit (tenant column required).

**BRANCH SCOPED:** sales, purchases, returns, claims, vouchers, cash_sessions, stock_transfers, stock_counts, devices, warehouses, document_sequences (when per-branch), journal_entries (branch of the document).

**WAREHOUSE SCOPED:** stock_movements, stock_balances, product_batches, transfer endpoints, POS device default warehouse.

Products are tenant-scoped (shared across branches) unless a later setting restricts selling. Stock is always warehouse-scoped.

### 3.8 IDOR risks (explicit)

| Risk | Mitigation |
|---|---|
| Cross-tenant ULID guess on sale/product/customer | Tenant scope + 404 |
| Cross-tenant child ULID (`sale_items`) | Child `tenant_id` + parent FK check |
| Cross-branch sale ULID for a cashier | Branch scope; 404 |
| Cross-branch warehouse on a sale post | Device/session warehouse; warehouse.branch_id must match |
| Swap `sale_id` on a return line to another tenant’s item | Original line must belong to original sale of this tenant |
| `Model::findOrFail` without scope | Banned in tenant HTTP |
| Platform admin hitting `/api/v1/*` | No membership → 401/403; no silent financial read |

- TanStack Query: server data
- Dexie: offline business data and outbox
- Zustand: open tabs, active ribbon, focus, sync indicator only
- localStorage: harmless UI prefs only (theme, last ribbon). **Never transactions, stock, or balances.**

## 6. Financial write pipeline

Posted sales, purchases, payments, vouchers, stock adjustments, and similar documents are **immutable**. Corrections: VOID, REVERSAL, RETURN, DEBIT NOTE, CREDIT NOTE, ADJUSTMENT.

### 6.1 Sale posting (atomic)

One `DB::transaction()`. **No partial posted sale may survive.**

1. Resolve tenant/branch/warehouse from membership/device (not payload trust).
2. Validate authorization (permission + branch + warehouse hierarchy).
3. Validate invoice state (not already posted; hold/draft/offline completed).
4. Obtain idempotency protection: **INSERT** `(tenant_id, idempotency_scope, idempotency_key)` as `started`. Unique violation → lock existing row; same fingerprint replays; different fingerprint `IDEMPOTENCY_KEY_REUSED`. Never SELECT-then-INSERT without the unique constraint.
5. Lock inventory `stock_balances` rows and required `product_batches` with `lockForUpdate()`.
6. Recalculate price, tax, discount, quantities, payments, COGS server-side (BCMath). Ignore client totals.
7. Validate stock (and expiry/FEFO rules).
8. Create `sales` row (not posted until the end of the same transaction).
9. Create `sale_items`.
10. Create `sale_payments` allocations.
11. Create `stock_movements` (`SALE`).
12. Update `stock_balances` projection (not independent truth).
13. Create balanced `journal_entries`.
14. Create `journal_lines` (assert Σ debit = Σ credit).
15. Finalize canonical `document_no` from locked `document_sequences`.
16. Mark sale and journal `posted`; write audit.
17. Commit. Persist idempotent response after commit (or in-transaction with the row).

Any error: **ROLLBACK EVERYTHING.**

### 6.2 Purchase posting (atomic)

Same transaction discipline:

1. Resolve tenant/branch/warehouse from session.
2. Authorize `purchases.post` + branch/warehouse ownership.
3. Idempotency insert/lock.
4. Recalculate line and landed cost (freight, loading, transport, tax) server-side.
5. Lock destination `stock_balances` / batches.
6. Create purchase + items.
7. Create or update `product_batches` (number, expiry, received cost, warehouse).
8. Insert `PURCHASE` movements; increase cache.
9. Create supplier payable and/or payment lines.
10. Create balanced journal (inventory / AP or cash).
11. Allocate `document_no`; mark `posted`; audit; commit.

A purchase must not remain `POSTED` if inventory or accounting failed.

### 6.3 Returns

Return qty ≤ original line qty − already **posted** returned qty. Concurrent returns `lockForUpdate()` the original sale/purchase and its lines (or a per-line return accumulator) before validating.

Preserve: original document ULID, original line ULID, returned qty, reason, approval, stock reversal, accounting reversal.

Details: `docs/ACCOUNTING.md`, `docs/INVENTORY.md`.

## 7. Offline

POS terminals continue **cash** sale, hold, search, and local print without the network. IndexedDB via Dexie. Outbox sync. Server is source of truth. IndexedDB is **untrusted**; every sync payload is fully revalidated.

**v1 commercial safety**

- Offline **credit sales disabled** unless tenant setting `allow_offline_credit_sales` is on, with snapshot credit-limit checks and `as of` labels. Never unlimited offline credit.
- Offline **returns** only against an original invoice that is cached locally and still integrity-checkable; otherwise online.

See `docs/OFFLINE_SYNC.md`.

## 8. Time, reports, approvals

**Time:** All `created_at` / `updated_at` / `posted_at` are `TIMESTAMPTZ` stored in **UTC**. Tenant `business_settings.timezone` (and optional user override) is used for display. Financial **business date** (`document_date`) is a separate `DATE` in the tenant’s books — not `created_at`. Offline `created_at_device` is stored; server still sets UTC `created_at` and an authorized `document_date`.

**Reports:** Use posted data only. Draft, hold, and incomplete local tickets are excluded. Voided operational documents are excluded from “sales” totals; their reversing journals remain in the accounting ledger so books stay balanced. Inventory reports use posted movements only (void/reversal movements included so qty nets). See `docs/ACCOUNTING.md` § reports.

**Segregation of duties:** Optional, tenant-configurable approval (off by default for small marts) for: large discount, price override, stock adjustment/write-off, manual journal, large refund, purchase approval, database restore. Permissions stay split even when approval is off (cashier still lacks `sales.void` by default).

## 9. Security baseline

Sanctum sessions, CSRF on cookie SPA, policies on every mutation, tenant global scopes, Form Requests, hashed passwords, no secrets in git, PII-safe logs, stable production errors.

See `docs/SECURITY.md` and `AGENTS.md`.

## 10. Backup and destructive-command policy

Application “Database Management” may create encrypted backups, show status, schedule, retain, verify, and restore **with elevated permission, confirmation, and audit**.

The application and agents **must never** automatically run `DROP DATABASE`, `DROP TABLE`, `TRUNCATE` of business data, `db:wipe`, or `migrate:fresh` against development, shared, or production databases.

Every migration has a safe `down()` when the change is reversible.

## 12. Open architectural decisions

Resolved for v1 (do not reopen without a doc change):

| Topic | Decision |
|---|---|
| Process split | Modular monolith |
| Tenancy | Shared schema + `tenant_id` |
| Public IDs | `ulid CHAR(26) UNIQUE NOT NULL`; never a `uuid` column; `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` is internal only |
| API style | REST, not JSON:API |
| Costing | Moving weighted average |
| Categories | `categories` + `subcategories` tables (spec) |
| Sequences | `document_sequences` |
| Offline v1 | Cash sales, holds, local print, snapshot balances. Credit sales **off** by default. Returns only if original invoice is local. |
| Money / qty | `NUMERIC(20,4)` money, `NUMERIC(20,6)` qty |
| Journal status | `draft` / `posted` only. Reversal = **new posted** journal with `reverses_journal_entry_id`. Original stays `posted`. |

Deferred / to confirm at the named phase:

| Topic | Default | Confirm |
|---|---|---|
| Login identifier | Email globally unique; optional username | Phase 1 |
| Multi-tenant user | One user, many memberships | Phase 1–2 |
| Offline credit | Disabled unless `allow_offline_credit_sales` | Phase 15 |
| Offline price | Server recalculates at post; min-sale enforced | Phase 15 |
| Impersonation TTL | Time-limited session (default 30 min) | Phase 17 |
| Stock reservation | Not in v1 | Phase 16+ if oversell pain is high |
| FIFO costing | Not in v1 | After weighted average is proven |
| Serial numbers | Optional product flag, engine later | Phase 4+ |
| Super Admin UI | Separate route prefix in same SPA vs second app | Phase 17; same SPA `/platform` is enough |
| Print bridge | Browser print first; native agent later | Phase 6 / 20 |
