# BluePOS Implementation Roadmap

Greenfield commercial Multi-Mart POS. **Modular monolith.** No microservices.

**Current position:** Phase 2.5 account/device/session security. Phase 3 catalog is paused (files preserved). Do not start Phase 4 until a human explicitly asks.

A phase is **not** complete because a UI renders. Completion requires migrations, policies, tests, a changed-file report, command report, and test results — then stop for approval.

Working agreement before every phase:

1. Inspect existing implementation.
2. Explain what will change.
3. Implement the minimum coherent slice.
4. Add migrations with `down()` when safely reversible.
5. Add tests.
6. Run tests.
7. Report modified files, commands, and test results.
8. Stop.

**Never:** `DROP DATABASE`, unstructured `DROP TABLE`, `TRUNCATE` of business data, `db:wipe`, `migrate:fresh` on persistent databases.

## Phase 1 — Foundation

**Goal:** Runnable Laravel 13 API + React/Vite TypeScript shell + PostgreSQL + Sanctum session auth + tenant/branch/warehouse model with ULID public IDs.

**Scope**

- Monorepo `backend/` + `frontend/`.
- Ribbon (Definition, Daily Entries, Reports, Tools, Administration, Help) + tab workspace chrome.
- Login / logout / `GET /api/v1/me` / `GET /api/v1/health`.
- Tenant context from authenticated **membership** (create `memberships` now to avoid rework).
- Dev seeder: platform admin, one tenant, two branches, two warehouses, one tenant admin membership.

**Database changes**

- `tenants`, `users`, `memberships`, `branches`, `warehouses`, Sanctum tables.
- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` and `ulid CHAR(26) UNIQUE NOT NULL`. No money tables yet.

**Backend work**

- Laravel 13, PHP 8.3, PostgreSQL connection.
- Middleware `SetTenantContext`.
- Global `BelongsToTenant` on Branch/Warehouse.
- API resources by ULID.

**Frontend work**

- Vite + React + TS + Tailwind + Router + TanStack Query + RHF + Zod.
- Dense desktop shell, status bar (`navigator.onLine` only).
- No Dexie, no POS grid.

**Security requirements**

- Sanctum SPA cookies, CSRF, hashed passwords.
- Ignore client `tenant_id`.
- Cross-tenant branch ULID → 404.
- Stable error envelope.
- `.env` not committed.

**Tests**

- Login success/fail; throttle stub if cheap.
- Health.
- Tenant A cannot fetch Tenant B branch by ULID.
- Unauthenticated `/me` → 401.

**Exit criteria**

- `php artisan test` green against PostgreSQL.
- Frontend production build succeeds.
- Login returns user + membership + tenant.
- Isolation test documented as passing.

**Explicit exclusions**

- RBAC UI, products, POS, accounting, Dexie, Super Admin panel, Redis required, package work beyond this phase’s scaffold **after approval**.
- No `migrate:fresh` in README as a default habit.

## Phase 2 — RBAC

**Goal:** Users, roles, permissions, branch-scoped access, Role Management screen, last-admin guard.

**Scope:** Catalogue from `docs/PERMISSIONS.md`. Policies for existing resources. Audit log for identity events.

**Database:** `roles`, `permissions`, `role_permissions`, `membership_roles`, `membership_branches`, `audit_logs`.

**Backend:** Permission seeder, policies, last-admin protection, audit writer.

**Frontend:** Role screen (Available/Granted, Add/Remove/All, Copy, Save, branch scope). Users list.

**Security:** API 403 when cashier calls manage-users. No platform keys on tenant roles. Policies on every mutation.

**Tests:** Cross-tenant users 404; branch scope; last admin cannot strip `roles.manage`; unauthorized role blocked.

**Exit criteria:** Role save persists grants; policy tests green.

**Exclusions:** Products, POS, impersonation UI.

## Phase 4 — Inventory engine

**Goal:** Immutable movements, opening stock, `stock_balances` cache, batches/expiry.

**Database:** `product_batches`, `stock_movements`, `stock_balances`. Opening stock writes **movements + cache only**. Matching inventory journals wait for Phase 5 so posting services share one COA. **Do not invent a second accounting model.**

**Backend:** `InventoryService`, `lockForUpdate`, negative-stock setting, opening movement post.

**Frontend:** Opening stock grid; stock status; expiry colors.

**Security:** No PATCH qty on products; `opening_stock.post` / `inventory.view`.

**Tests:** Opening increases cache; negative blocked; no movement update API; concurrent lock test if feasible.

**Exit criteria:** Ledger + cache match for fixture; product qty field absent; **no sales module yet**.

**Exclusions:** Transfers, POS sales. Journal tables are Phase 5 (required before Phase 6).

---

## Phase 5 — Parties and COA

**Goal:** Customers, vendors, hierarchical accounts, `journal_entries` / `journal_lines`, opening AR/AP/cash/inventory journals. Balances derived from ledger.

**Database:** `customers`, `vendors`, `accounts`, **`journal_entries`, `journal_lines`**, `financial_years`. Backfill opening-stock journals for Phase 4 openings.

**Backend:** Opening balance poster; balance query service; COA seed on tenant provision.

**Frontend:** Customer/vendor forms; COA tree; opening balances; ledger screen stub.

**Security:** Cannot PATCH live balance; tenant isolation.

**Tests:** Opening AR balanced; customer balance = Σ lines; reject unbalanced journal.

**Exit criteria:** Journal poster exists; unbalanced journals cannot post; no editable party balance column. **Hard dependency for Phase 6.**

**Exclusions:** Full voucher UI (Phase 10), POS. Do not defer journals to Phase 10 — that would force a sales rewrite.

---

## Phase 6 — Sales POS

**Goal:** Barcode-driven sales, hold/recall, split payments, server-side totals, print skeleton, atomic post **using Phase 5 journals**.

**Prerequisite:** Phase 5 complete (COA + journal poster). Do not start Phase 6 without it.

**Database:** `sales`, `sale_items`, `sale_payments`, `document_sequences`, `cash_sessions` (open/close basic), `devices` (minimal if not earlier), `idempotency_keys`.

**Backend:** `SaleCalculator` (BCMath), `SalePostingService` (validate, lock, recalc, invoice, items, payments, movements, journal, commit), idempotency, sequences.

**Frontend:** Sales Invoice grid (configurable columns), barcode focus, F-keys, totals, hold/recall, 80mm print CSS.

**Security:** `sales.*` policies; ignore client net total; idempotency required; posted immutable.

**Tests:** Stock deducted; journal balanced; COGS posted; wrong client total still correct server net; split payments; hold does not move stock; duplicate Idempotency-Key; cross-tenant sale 404.

**Exit criteria:** All posting tests green; one complete cash sale in UI **and** matching DB rows (sale + items + payments + movements + balanced journal).

**Exclusions:** Offline Dexie posting, returns, Super Admin, offline credit.

## Phase 7 — Sales returns

**Goal:** Return against invoice (and without invoice with permission); qty cap; stock restore; reversing journal.

**Database:** `sale_returns`, `sale_return_items`.

**Backend:** Qty ≤ sold − returned; batch restore; `SALE_RETURN` movement.

**Frontend:** Return screen from original invoice.

**Security:** `sales_returns.*`; without-invoice gated.

**Tests:** Over-return rejected; stock restored; journal balanced; void rules.

**Exit criteria:** Fixture original + return consistent.

**Exclusions:** Purchase returns.

## Phase 14 — Offline / PWA foundation

**Goal:** Service worker, Dexie schema, snapshot pull, grants cache, status bar real states. **No financial outbox post yet** (or local draft only that cannot sync).

**Database:** Possibly `devices` completion; `sync_batches` stub.

**Backend:** `GET /sync/changes` chunked.

**Frontend:** Dexie stores per `docs/OFFLINE_SYNC.md`; last synchronized at.

**Security:** Device register; snapshots not in localStorage; tokens not in localStorage.

**Tests:** Sync pagination; snapshot tenant-scoped.

**Exit criteria:** Offline app shell loads; catalog searchable from Dexie after pull.

**Exclusions:** Outbox posting (Phase 15).

## Phase 15 — Offline sales and sync

**Goal:** Outbox **cash** sales through the documented state machine; estimated stock; snapshot balances.

**Security:** Idempotency; server recalc; permission/device re-check; IndexedDB untrusted; no live-balance claim; **credit sales rejected offline** unless future setting.

**Tests:** Replay no duplicate; dropped response retry; insufficient stock conflict; credit offline rejected; return without local original rejected.

**Exclusions:** Offline credit (default), offline returns without local invoice, purchases offline, conflict UX polish (Phase 16).

## Phase 16 — Conflicts, devices, hardening

**Goal:** Device revoke, conflict inbox, optimistic versions, rate limits, headers, concurrent oversell test.

**Database:** `sync_conflicts`; devices full fields.

**Backend:** Revoke invalidates tokens; conflict APIs.

**Frontend:** Device admin; conflict manager screen.

**Security:** Full `docs/SECURITY.md` headers, throttles, `DEVICE_REVOKED`.

**Tests:** Revoked device cannot post; concurrent checkout cannot oversell; idempotency reused payload.

**Exit criteria:** Hardening tests green.

**Exclusions:** Licensing UI.

## Phase 17 — Super Admin, licensing, subscriptions

**Goal:** Platform UI: tenants, plans, `tenant_modules`, subscriptions, status, trials, limits, health, version, support notes. Impersonation with reason + audit + banner.

**Database:** `plans`, `subscriptions`, `tenant_modules`, `support_impersonations`.

**Backend:** Platform routes; default deny tenant documents.

**Frontend:** `/platform` app section.

**Security:** No casual financial access; impersonation requirements.

**Tests:** Platform admin GET sale 403/404 without impersonation; impersonation without reason fails; ended session cannot continue.

**Exit criteria:** Activate/suspend tenant; limits enforced on branch/user/device create.

**Exclusions:** Payment gateway billing (manual/subscription records first).

## Phase 19 — Performance and security audit

**Goal:** Index review, hot query EXPLAIN, 100k product search path, IDOR sweep, N+1 on POS search, CSP, cache drift job.

**Database:** Additional indexes / `pg_trgm` if justified. No destructive rebuild.

**Backend:** Query optimization; security checklist against `docs/SECURITY.md`.

**Frontend:** Debounce, virtualized grids if needed.

**Security:** Full matrix test; `APP_DEBUG` production behavior.

**Tests:** Permission matrix; cross-tenant sweep; search pagination.

**Exit criteria:** Written audit notes in `/docs` addendum or PR; tests green.

**Exclusions:** Rewriting architecture to microservices.

---

## Phase 20 — Production deployment and backups

**Goal:** Encrypted backup, schedule, retention, verification, restore workflow with authorization and rehearsal. Deploy docs (HTTPS, Redis, queues, secrets).

**Database:** Backup metadata table if needed. **No drop-database UI.**

**Backend:** Backup jobs; restore requires `backups.restore` + confirmation token.

**Frontend:** Tools → Database Management.

**Security:** Encrypted backups; credentials never in frontend; restore audited.

**Tests:** Unauthorized backup 403; restore without confirm 403.

**Exit criteria:** Documented restore rehearsal; health check; queue worker documented.

**Exclusions:** Automatically running `migrate:fresh` anywhere.
